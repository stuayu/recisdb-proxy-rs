# recisdb-proxy 全体レビュー (2026-07)

対象: ワークスペース全体 (recisdb-proxy / bondriver-proxy-client / recisdb-protocol / recisdb-rs / b25-sys)
観点: 機能の追加・削除、パフォーマンス、セキュリティ、安定性、デバッグ可能性

関連: 設計の正本は [DESIGN.md](DESIGN.md) を参照。本書は「何を変えるべきか」の提言に特化する。

## 1. 総評

コア機能(チューナー共有・優先度/排他制御・グループ選局・自動スキャン・Webダッシュボード)は実装が揃っており、
パフォーマンス面もリングバッファのCondvar化・TSファストパス・チャンネル切替のACK先行化など実運用起点の改善が積み重なっている。

一方で以下の構造的な課題がある。

1. **セキュリティが「宅内LAN性善説」前提** — プロキシ本体もWeb APIも認証が一切なく、
   Web APIから外部コマンド(tsreplace)の実行パス・引数を書き換えられる。
2. **ドキュメントと実装の乖離** — READMEが謳うTLSはサーバー側で未結線。設計docの多くは時点レポートで、正本がなかった(→ DESIGN.mdに集約済み)。
3. **デッドコード整理は完了** — `metrics.rs`、`pool.rs`の未使用`MuxKey`、`docs/out`生成物を削除済み。
4. **session.rs の責務分割を実施** — 容量制御・退避・runtime・空間キャッシュ・グループ候補・引き継ぎを専用モジュールへ分離した。
5. **Graceful shutdownは実装済み**。実機を使う統合テストハーネスは引き続き課題。

## 4. 新規追加すべき機能

### 4.1 安定性(優先度: 高)

1. **Graceful shutdown** — 現状 `ctrl_c`/signal ハンドリングが無い。
   `tokio::signal` + `CancellationToken`で「新規接続停止 → セッションにStopStream → BonDriver CloseTuner → DB flush」の順序で停止。
   Windowsサービス/systemd Type=notify対応もここに乗る。
2. **統合テストハーネス** — `MockTuner`(ダミーTSを吐くBonDriver実装)をtuner enumに追加し、
   `tests/integration_test.rs`で「接続→選局→ストリーム→退避→切断」のシナリオテストを実施。
   session.rsの退避ロジック(ClientConnectionSequence.mdのバグの類)は回帰テストがないと再発する。
3. **リーダータスクのwatchdog** — `SharedTuner`の読み取りループが無応答になった場合の自動再起動(現在はstop時タイムアウトのみ)。
4. **DLL側の全エクスポートを`catch_unwind`でラップ** — 現在`CreateBonDriver`のみ。FFI境界を越えるパニックはUBなので全境界で必須。

### 4.2 デバッグ可能性(優先度: 高)

1. **Prometheus `/metrics` エンドポイント** — `axum`に`metrics-exporter-prometheus`を追加し、
   セッション数・ドロップ率・ビットレート・チューナー稼働をエクスポート。Grafanaで時系列監視でき、
   独自の`metrics_history`(VecDeque)より運用実績のあるスタックに乗れる。
2. **`tracing`のspan活用** — セッションID・ChannelKeyをspanフィールドにし、`RUST_LOG=...`でなく
   `tracing-subscriber`のEnvFilter+JSON出力(`--log-format json`)を選択可能に。障害時のgrepが激変する。
3. **プロトコルレベルのデバッグダンプ** — フレーム単位のhexダンプをTRACEで出せるように(クライアント/サーバー両方)。
   TVTestクラッシュ調査の度に毎回アドホックにやっている作業の恒久化。
4. **クラッシュレポート** — DLL側でパニック時にミニダンプ相当(バックトレース+直近ログN行)を`%TEMP%`に保存。

### 4.3 最新技術・エコシステム(優先度: 中)

1. **Mirakurun互換API(サブセット)** — ✅ **実装済み (2026-07-04, STREAMING_DESIGN.md §7.1 P6)**。
   `web/mirakurun.rs` + `/mirakurun/api/*` (`GET version/status/channels/services`,
   `GET services/:id/stream`, `GET channels/:type/:channel/stream`)。`/api/programs` 相当の EPG は
   未実装のまま(意図的にスコープ外)。`/api/*` とは別ルータで無認証・`[mirakurun] enabled=false` 既定の opt-in
   (理由: 実 Mirakurun クライアントは Authorization ヘッダを送らないため、既存の認証必須 `/api/*` 配下には
   置けない)。詳細は STREAMING_DESIGN.md §11 の P6 実装メモを参照。
2. **WebSocket / SSEによるダッシュボード更新** — 現在5秒ポーリング。axumの`ws`でプッシュ化し、
   ビットレート/シグナルのグラフをリアルタイム化。
3. **設定のホットリロード** — tuner_config/scan_configはDB経由で反映されるが、TOML側(listen等以外)も
   `notify` crateでリロード可能に。
4. **sqlxまたはrusqlite+r2d2への移行検討** — 現状`Arc<tokio::sync::Mutex<Database>>`の単一コネクション。
   まずはWAL化(§5)で足り、プール化は計測してから。

## 5. パフォーマンス改善

| # | 施策 | 根拠 | 期待効果 |
|---|------|------|---------|
| 1 | **SQLite WAL + busy_timeout** | 現状`journal_mode`未設定(デフォルトdelete)。単一Mutex越しにWeb API・セッション・スキャナが同一コネクションを奪い合う | 読み書き並行性向上、ロック待ち削減。`PRAGMA journal_mode=WAL; PRAGMA busy_timeout=3000;` の2行から |
| 2 | **DBアクセスの`spawn_blocking`分離** | rusqliteは同期I/O。tokioワーカーをブロックしTS配信のレイテンシに波及しうる | 配信ジッタ削減 |
| 3 | **TsDataのゼロコピー化の徹底** | `ServerMessage::TsData { data: Vec<u8> }`はエンコード時にコピーが発生。フレームヘッダ+`Bytes`のchainで送出し、broadcastの`Bytes`をそのまま流す | セッション数×チャンクサイズ分のmemcpy削減 |
| 4 | **チャンネルリスト/space解決のキャッシュTTL** | `ensure_channel_map()`がセッション毎にDBを引く。GroupSpaceInfoの構築もDB全読み | 選局レイテンシ削減(グループ利用時) |
| 5 | **driver_quality_statsのスコアをselectorに接続** | スコア計算は信号強度と負荷のみ。DBに品質統計があるのに未活用 | 質の悪い個体を自動的に避ける実質的な負荷分散 |
| 6 | **クライアントDLLの読みバッファ/リングバッファ計測** | Round 1-3の改善(Condvar化、256KB読みバッファ)後の実測値が残っていない | ベンチ記録をdocs/perfに残し、以後の変更の判断基準にする |

## 6. セキュリティ改善(優先度順)

### S1. tsreplace設定経由のRCE(最重要) — **実装済み (2026-07-04)**

`POST /api/tsreplace-config`(無認証)で`command_path`と`arguments`を書き換えられ、サーバーが
`Command::new(command_path)`で実行する(session.rs:426)。**LAN内の誰でも、あるいはCSRF経由でブラウザからでも任意コマンド実行が可能**。

対策(併用):
- Web APIに認証を導入するまで、`command_path`はTOML設定ファイル側でのみ変更可能にする(API/DBからは引数のみ、あるいは読み取り専用)。
- 実行前に`command_path`を絶対パス+存在確認+許可リスト照合。

**実装内容**: `UpdateTsreplaceConfigRequest`(`web/api.rs`)から`command_path`フィールドを削除し、
リクエストに含まれていても無視され既存のDB値が維持される。`command_path`を変更できるのは
`Database::set_tsreplace_command_path`(`database/mod.rs`)のみで、これは起動時に`main.rs`が
TOML `[tsreplace] command_path`から一度だけ呼ぶ経路に限定されている(APIハンドラからは到達不可)。
ダッシュボードの実行コマンド欄も読み取り専用表示に変更。`command_path`を絶対パス+存在確認+
許可リスト照合する追加対策は未実装(スコープ外、将来のP2以降で検討)。

### S2. Web ダッシュボードの無認証+permissive CORS — **実装済み (2026-07-04)**

`CorsLayer::permissive()`かつ認証ゼロ、デフォルトbind `0.0.0.0:40080`。切断・DB書き換え・スキャン起動が誰でも可能。

対策:
- **APIトークン認証**(`Authorization: Bearer`)を全`/api/*`に。トークンは初回起動時に生成しTOMLへ。
- CORSを同一オリジンに限定(ダッシュボードは同一サーバー配信なのでCORS自体ほぼ不要)。
- デフォルトbindを`127.0.0.1`にし、LAN公開は明示オプトイン。

**実装内容**: `web/auth.rs`に`require_auth`ミドルウェア(`axum::middleware::from_fn_with_state`)を追加し、
`/api/*`(`build_api_router()`)のみに`route_layer`で適用。トークンは起動時に
TOML `[web] auth_token` > DB `web_auth_config`テーブル(永続化済みの値) > 新規生成、の順で解決し、
新規生成時のみ起動ログに一度だけ表示(`main.rs`)。生成は新規クレートを追加せず、
`std::collections::hash_map::RandomState`(OS CSPRNGでシードされることがstdで保証されている)を
複数回独立採取してハッシュする方式(`web/auth::generate_token`)。`[web] auth_enabled = false`で
無効化可能(無効時はWARNログ)。ダッシュボード側は初回`prompt()`でトークン入力→`localStorage`保存→
`window.fetch`をラップして全`/api/*`呼び出しに自動付与、401時は再入力を促す(`dashboard.rs`)。
CORSは`CorsLayer::permissive()`を削除し、レイヤー自体を外した(同一オリジンのみで十分なため)。
`web_listen`の既定は`127.0.0.1:40080`に変更(P0と共通実装、下記参照)。
プロトコル側のPSK認証(S3)は本タスクのスコープ外で未着手。

### S3. プロキシプロトコルの無認証

`Hello { version }`のみで誰でもチューナーを使え、`exclusive=true`で他人の録画を退避できる。

対策:
- プロトコルv2として`Hello`に**PSK(事前共有鍵)ベースの認証**を追加(HMACチャレンジレスポンスで平文鍵を流さない)。
- サーバー側で**クライアント毎の優先度上限**を設定可能に(視聴用クライアントがpriority=255を自称できないように)。
- 接続元IP許可リスト(`allowed_networks = ["192.168.0.0/24"]`)。

### S4. TLSの実装完了(または撤去)

サーバー側accept経路に`tokio_rustls::TlsAcceptor`を結線し、`require_client_cert`(mTLS)を機能させる。
実装しない間はREADME・QUICKSTART・設定例からTLS記述を外す。「暗号化されているつもり」が一番危険。

### S5. その他の堅牢化

- プロトコルデコーダを`cargo-fuzz`でファジング(未認証入力の16MBフレームを扱うため)。
- `cargo audit` / `cargo deny` をCIに追加(rustls 0.22, tokio 1.35 など依存が固定化しつつある)。
- Web APIの入力(チャンネルimport等)のサイズ・件数上限。
- セッション数上限は`max_connections`があるが、**IP毎の上限**とハンドシェイクタイムアウトを追加。
